# The honest countdown: estimating wait time over a volunteer GPU queue

This is an engineering write-up of a quieter problem in [SIXFINGERS](https://sixfingers.art) than the one in [The grey squares](grey-squares.md), and in some ways a harder one, because it has no correct answer. The pictures are generated by the [AI Horde](https://aihorde.net), a network of volunteers who run image models on their own graphics cards for free. That makes the site free, and it makes the wait unpredictable: a wash can take forty seconds or four minutes depending on who happens to be online and what they have loaded. Most sites paper over a wait like that with a spinner. I wanted the wait to be a readable part of the experience instead, which meant putting a real number on something genuinely uncertain, and being honest about it.

The constraint I set for myself was simple to state and hard to meet: announcing a time is a promise that it will not be longer. A countdown should behave like the one on a real washing machine. It should only ever go down, it should reach zero exactly when the machine stops, and it should never invent a figure it cannot stand behind. Everything below follows from taking that seriously over a queue nobody controls.

## Two waits, not one

The first thing the recorded washes showed is that "the wait" is two different things with different behaviour, and treating them as one number is why the early versions felt dishonest.

There is the line: the time until a volunteer picks the request up. It is long and it does not predict to the second, running anywhere from forty seconds to two minutes on a normal evening, and much longer when few volunteers are online. Then there is the work: once a request is picked up, the six pictures of a wash come back within twelve to thirty-three seconds of each other. The work is short and fairly stable. The line is the uncertain part, and it is almost the whole wait.

So a machine estimates the two separately and adds them. The work becomes a fixed "ritual" of thirty-five to seventy seconds (the model's usual render time, a little air, and a twelve-second spin), and all the real modelling goes into the line.

## What actually predicts the line

The obvious signal is the wrong one. The Horde publishes a global queue, often six or seven hundred requests deep, and reading that number makes it look as though hundreds of people are ahead of you. They are not, because each volunteer only serves the models they have loaded, so most of that queue is waiting for other machines entirely. On the evenings I recorded, the global queue predicted the real wait about as well as a coin.

What predicts the line is the number of requests waiting for this specific model divided by the number of volunteers running it. Seven requests against two computers is a long wait; seven against eight is quick. Measured across sixty-two real anonymous washes, that ratio correlated with the actual wait at 0.83, against 0.75 for the raw request count and essentially nothing for the Horde's global queue or throughput.

The line estimate is therefore a regression on that ratio, in log space because the wait grows faster than linearly as a queue backs up onto few workers:

```js
// v.queued = requests waiting for this model; v.workers = volunteers running it.
// file = line, R.marge = a learned safety margin that keeps the estimate on the high side.
const r = (v.queued || 0) / Math.max(1, v.workers);
let file = Math.exp(R.a + R.b * Math.log(1 + r) + Math.max(0, Math.min(1.2, R.marge)));
file = Math.max(12, Math.min(900, file));   // at least time to be picked up, at most 15 min announced
return { file, rite, total: file + rite };
```

The coefficients are not constants baked into the code. The Horde is a different place from one day to the next, so `a`, `b` and the margin are refit from the last forty anonymous washes and handed back to the site, with a measured default to fall back on when there is not enough recent data. The margin is the honest part: it is set so the announced time lands above the real one roughly seven times in ten, because an estimate that is usually a little pessimistic keeps the promise, and one that is usually optimistic breaks it. This fifth version of the estimate, measured before it shipped, carries a typical error of about 1.9x, down from 2.5x under the earlier additive rule it replaced, and it dropped the per-machine floors and multipliers that version had accumulated, which were stacking caution on caution.

## Rules for a countdown that only goes down

A good estimate is half of it. The other half is how the countdown behaves once it is running, because the estimate will be wrong, and the whole promise lives in how the clock handles being wrong.

While you are in line, the clock descends at the speed of a real clock and never climbs. If the line is running a little slower than announced, the ritual is allowed to compress toward its thirty-five-second floor to absorb the slack without the number ever moving the wrong way. If it reaches that floor and a volunteer still has not picked the request up, the site does not silently invent a new number. It says so, once or at most twice, and then it stops guessing:

```js
// still in line, and the clock has run down to the ritual's floor:
// name the delay, once or twice at most, then hold rather than invent a figure.
if (e.fin <= seuil) {
  if (e.contretemps < 2) { e.fin = seuil + (e.contretemps ? 60 : 30) * 1000; e.contretemps++; }
  else e.fin = seuil;                 // hold on "any moment" instead of a made-up time
}
```

Underneath that, the clock also listens to the Horde itself. Twelve seconds into the line it begins comparing its own estimate with the Horde's estimate for the first of the six requests, the one that starts the wash. If the Horde expects less time, the clock eases down toward it smoothly. If the Horde expects much more, the clock climbs, but only in steps of at most a minute, announced on the card ("busy line: few volunteers on this machine"), one step every twenty seconds, never a jump. The difference between a jump and a step is the difference between a clock you distrust and one you forgive.

That correction exists because of a specific failure. A machine with only two or three volunteers behind it breaks the model, because anonymous requests are served after people who hold Horde priority points, so a wash announced at a minute and a half can sit in line for nine minutes while higher-priority work goes first. The stepped correction is how the clock stays honest in that case without lurching.

When a volunteer finally picks the request up, that is treated as its own moment, with a sound and a "your turn", and from there the time is the site's own to spend. The ritual takes whatever the clock had left rather than a fresh duration, capped so it can never be longer than what was already on display:

```js
// servir: a volunteer has taken the request. the ritual takes what the clock still showed,
// never more than that, so the number drops at most and never climbs.
servir(now) {
  e.servi = now;
  const reste = (e.fin - now) / 1000;                       // time the clock still showed
  const voulu = Math.min(reste, (e.rite || RITE_MIN) + 10);
  e.fin = now + Math.max(e.riteMin, Math.min(RITE_MAX, voulu)) * 1000;
}
```

Because of that cap, being picked up early does not make the clock jump. It keeps descending, the six pictures are spread across whatever time remains, and it reaches 0:00 exactly as the spin ends and the machine stops. The one thing that can freeze it is a picture that genuinely has not arrived when it is due, and a frozen clock waiting for a real event is honest in a way a moving clock inventing progress is not.

## It learns from the washes it got wrong

None of these numbers would stay right on their own, so after every real wash the site sends back what actually happened, with no identifier: the machine, how the wash ended, the time it had announced, and the line and the work as they really were, alongside the state of the Horde when it started. That record is what the nightly refit learns from. The estimate is not a formula I tuned once; it is a formula that is re-derived from the most recent washes the site has seen, so that when the Horde's population shifts the margins move with it. The parts of the system that could drift are the parts wired back into their own measurements.

## The lesson

The interesting part of this was not the regression. It was accepting that an estimate over something you do not control is a product decision before it is a mathematical one, and that the decision is which way to be wrong. A number that is usually a touch pessimistic and never climbs reads as trustworthy even when it is off by a minute; a number that is accurate on average but sometimes doubles reads as a lie. Every rule here, the high-set margin, the clock that only descends, the stepped correction, the refusal to invent a figure once it runs out, is a choice to spend accuracy on trust.

The two lessons I would carry to another project: measure the thing itself rather than trusting the provider's own estimate, which here was wrong by a factor of twenty in the worst case I recorded, and decide in advance how a number is allowed to behave when it is wrong, because that behaviour, not the average error, is what people actually feel.
